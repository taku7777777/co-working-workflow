# 計器の欠損経路の実測 — 「セッション末尾の AI 応答が記録されない」の原因

日付: 2026-08-02

検11(b) の原因調査。K1 自己盲検(2026-08-01)で観測された
「セッション末尾の AI 応答が記録されておらず、直前の依頼者発言への対応結果が brief から確定できない」
(`work/2026-08-01-k1-self-blind/record.md` 3番)の原因を、実データの突合で特定した。

**結論を先に言うと、K1 が見たものは hook の不発ではなかった。記録は失われておらず、
別のスレッドに書かれていた。** 原因は独立した3つの経路に分かれる。

## 方法

この環境には、cowork とは独立に **hook の生ペイロードを全件保存している第二の計器**がある
(`~/.metsuke/ledger.db` の `hook_event` テーブル。metsuke の `hook-sensor.sh` が
`~/.claude/settings.json` のグローバル hook で cowork と並んで発火している)。
これを cowork-state と突き合わせることで、「hook が発火しなかった」のか
「発火したが cowork が記録しなかった」のかを初めて切り分けられた。

- 期間の Stop イベント: 1,446件 / UserPromptSubmit: 1,587件 / セッション: 293
- 照合先: `~/cowork-state/**/sessions/*.jsonl`(149セッション・18スレッド)
- 実在確認: Claude Code の transcript(`transcript_path`)を直接読み、
  応答が実在するかを判定(sidechain = サブエージェントの発話は除外し、
  tool_result の user エントリは会話の区切りとして数えない)

## 経路1: スレッド分裂 —— K1 が観測したのはこれ

**セッションの途中でブランチが変わると、同一セッションの記録が複数のスレッドに分かれて書かれる。**
cowork はレコード単位で repo+branch からスレッドを解決するため、
ブランチを切り替えた時点から後の記録は別スレッドのディレクトリに入る。

K1 の実例(セッション `836f6879`):

| 時刻(UTC) | ledger の Stop | cowork の記録先 |
|---|---|---|
| 2026-07-26 21:37 | 4,028字 | `unfiled/metsuke/0001-workshop-prep-002` |
| 2026-07-26 22:19 | 1,734字 | 同上 |
| 2026-07-26 22:37 | 1,254字 | 同上 |
| **2026-07-26 23:22** | **1,287字** | **`unfiled/metsuke/docs-auto-gate-denial-observed`** |

4回目の Stop は正常に発火し、1,287字の本文も渡っていた。cowork も正常に記録した。
ただし**別のスレッドに**記録したため、K1 が読んだスレッドの brief では
そのセッションが応答なしで終わったように見えた。

影響範囲(`precheck` は複数リポジトリに同名で現れる擬似セッション —— 正本 §2.2 が既知として
挙げている類型 —— なので、実セッションではないものとして除外した):

- 分裂しているセッション: **5 / 148(3.4%)**
- **そのせいで不完全になっているスレッド: 9 / 17(53%)**

セッション側の比率は小さいが、1本の分裂セッションが触れたスレッドすべてを不完全にするため、
スレッド側で見ると影響は桁違いに大きい。

### この現象をどう読むか —— 2つの読み方があり、証拠はどちらを支持するか

**読み方A「スレッド解決が壊れている」。** 規8「スレッド1本 = PR 1本 = 400行以下」に従うと、
1セッションの中でブランチを何度も切り替えることになる。実際、この記録を書いているセッション自身が
3スレッド(`0006-solution-catalog` / `0007-doc-consolidation` / `0008-three-instruments`)に
分裂している。規約を守るほど分裂する。

**読み方B「仕様どおりに動いている」。** `cowork/README.md` は brief の解決を
「現在のリポジトリとブランチから」と定めており、規8 は1スレッド = 1ブランチと定めている。
この2つの下では、3ブランチにまたがるセッションが3スレッドに分かれるのは**設計の正常な実行**である。

**証拠が強制するのは、どちらの読み方でも成り立つ、より狭い結論のほうである:**

> **記録は正しく仕分けられている。壊れているのは表示である。**
> `cowork brief <thread>` は、続きが別スレッドにあるセッションを「そこで終わったセッション」として
> 描画し、**続きがあることを示す信号を一切出さない。**

この区別は処方を分ける。A を採れば「セッション単位でスレッドを固定する」— 規8 と衝突する。
B を採れば「brief に継続の1行を出す」— 衝突しない。**どちらを採るかはここでは決めない**
(検証前の事前登録の外にある案なので、カタログに事後案として登録してから判断する)。

## 経路2: Stop hook の不発

**応答が実在するのに Stop hook が発火しないセッションがある。**

- 末尾の UserPromptSubmit に対応する Stop が無いセッション: 32 / 293
- そのうち transcript に**実際の応答が存在する**もの(= 記録の喪失): **18(全体の 6.1%)**
- 残り14件は応答自体が無い(中断)ので欠陥ではない

分裂とは違い、**この経路ではデータが本当に失われる**(cowork は呼ばれていないので書きようがない)。

性質:

- 18件中 **16件がプロンプト1件のみのセッション**。cwd の内訳は `data` 10件・`tmp` 3件で、
  スクリプトからの非対話起動(`claude -p` 相当)が主
- 圧縮(PreCompact / PostCompact)との相関はほぼ無い(18件中1件のみ)
- 対話的な開発セッション —— つまり cowork が実際に測る対象 —— での発生は少ない

**なぜ発火しないかは特定できていない。** 非対話セッションで Stop の発火前にプロセスが終了する、
という仮説と整合するが、追加の計装なしにこれ以上は詰められない。

## 経路3: payload に `last_assistant_message` が無い

Stop 1,446件のうち **11件(0.76%)** で `last_assistant_message` フィールド自体が存在しない。
`cowork/src/cli.ts` の Stop 分岐はこの場合に**無言で `return 0`** する
(空文字も同じ扱い。空文字のケースは0件だった)。

件数は小さいが、**エラーログにも残らない**ため、起きたことに気づく手段が現状ない。

## 副次的な発見

`~/cowork-state/capture-errors.log`(全16行)の内訳:

  そのレコードは失われている

## Run 2a への含意

1. **経路1 は Run 2a の測定を直接壊す。** OP がセッション中にブランチを切り替えると、
   JN に渡す brief はそのセッションの一部を欠く。JN は「brief の欠陥」として記録するが、
   実際には brief の設計ではなくスレッド解決の問題であり、**帰属の判定を誤らせる**
   (捕捉層 [B] に見えるが、実体は別の層)。
2. **検11(a) の全滅検知はこの3経路をどれも検知しない。** 閾値による乖離検査が捕まえるのは
   hook の完全死(pnpm のパス破壊・hook 仕様変更)であって、分布的な取りこぼしではない。
   検11 を実施しても、ここに書いた穴は塞がらない。
3. 最も安価な当座の対処は、**OP が brief を貼る直前に、そのセッション ID が他のスレッドにも
   書かれていないかを確認すること**(検11(c) の目視手順に1項目足すだけで済む)。
   **ただしこれは事後案である** —— カタログ(`work/2026-08-01-solution-space/catalog.md`)の
   事前登録に含まれていない。採否は事後案として登録したうえで判断すること。
