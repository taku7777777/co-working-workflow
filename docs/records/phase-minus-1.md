# Phase -1: 合流の予行演習

日付: 2026-07-25(初版コミット日。第8版 §12.1 により 2026-08-01 付与)
更新: 2026-08-02(本文は当時のまま。§2 に2箇所・§4 §5 §6 に各1箇所の注記を追加。
現行の記録シートは `docs/record-sheet.md`、現行の判定表は `docs/run-2a.md`)

**ツール不要・コスト0・1週間。** proposal.md の全体がこの検証に乗っている。
ここで得られる答えが、**そもそも何を作るか(あるいは作らないか)を決める。**

---

## 1. 何を確かめるのか

> **人が書いた数行の意図と指示履歴だけで、別の人がその作業に合流して続きを進められるか。**

proposal.md は「AIへの指示と判断を共有すれば、実装物を読まなくても状況を把握でき、
途中から一緒に進められる」という仮説に立っている。この仮説が偽なら、
どんなツールを作っても効かない。逆に真なら、**最も高価な自作部分が不要になる可能性がある。**

### 結果の読み方は直感と逆になる — 先に読んでおくこと

| 結果 | 意味 | 次の判断 |
|---|---|---|
| **数行のメモだけで引き継げた** | 軽量な共有で足りている | **最大の自作部分(セッション履歴の移送=Join)を作らなくてよい。** 自作は「指示ログ + 一覧UI」の2点に縮み、非公式機構への依存リスクごと消える |
| 引き継げたが何度か質問が要った | 足りない情報が特定できた | その項目をテンプレートに追加する。まだ Join は不要 |
| **セッションの中身を見ないと無理だった** | 重い合流に価値がある | Join を作る。ただし公式に維持義務のない機構への依存を承知で負う |

**「うまくいった」は「先に進む許可」ではなく「作らずに済む証拠」でありうる。**
ここを取り違えると、要らないものを8週間かけて作ることになる。

---

## 2. 手順

対象は **次の2〜3タスク**。普段どおり Claude Code で作業し、以下を足すだけ。

### ステップ1 — 作業者: 着手時に「意図メモ」を書く(3分)

作業を始める前に、下のテンプレートを共有ドキュメント(Slack・Notion・GitHub issue、どこでもよい)に貼る。

### ステップ2 — 作業者: 区切りで「指示履歴」を貼り足す(1分)

**AIに出した指示だけ**をコピーして追記する。AIの出力は貼らない。
実測では1セッションあたり数件・数百字にしかならないので、負担はほぼない。
参考までに、この提案書を作った一連のセッションでも、**人間の指示は3件だけ**だった。
それだけの分量しか出てこないのが正常。

**手で貼る代わりに `cowork brief` を使ってよい**(推奨。MVP-0 で実装済み。README 参照)。
hook を登録しておけば指示は自動で溜まるので、区切りで次を実行して**出力をそのまま貼る**だけになる。

```bash
cowork brief          # カレントブランチのスレッド。§3 のテンプレートの形で出る
```

方針(§3の「方針」欄)は `docs/cowork/<thread_id>/intent.md` に置いておけば brief に載る。
「判断したこと」「現在地」は自動では埋まらないので、そこだけ手で書く。

> (→ 2026-08-02 部分撤回。Tier 0 到達により「判断したこと」は kind:answer として自動捕捉され、
> brief の判断節に載るようになった。手で書く必要が残るのは「現在地」だけである
> — 捕捉側の自動要約は Tier 2-2 に属し、Phase -1 の判定まで凍結中。
> 経緯: work/2026-08-01-solution-space/catalog.md 文2)

> **これは実験の中身を変えない。** 測っているのは「そのメモで引き継げるか」であって
> メモの作り方ではない。むしろ手で選ぶより指示が漏れないので、条件としては素直になる。
>
> **cowork が使えなくても Phase -1 は止めない。** その場合は手でコピーする。
> ツールの用意を待って検証が遅れるのは本末転倒である。

### ステップ3 — 合流する人: メモだけを読んで続きをやる

**重要: 作業者に口頭で聞かない。** メモだけで足りるかを測る実験なので、
分からないことがあったら「聞かずに済ませられなかった項目」として記録する。
どうしても詰まったら聞いてよいが、**何を聞いたかを必ず記録する**(これが最も重要なデータ)。

そのうえで、自分の Claude Code で続きを進める。

> (→ 2026-08-02 撤回。K1 自己盲検(2026-08-01)で、人間がメモ(brief)を直接読み下す形は
> 非現実的と実測された(18.6KB)。仮説は H2「brief は AI が消費し、人間は AI の統合・説明を介して
> 合流する」へ移行し、Run 2a では合流者は brief を**自分の AI に渡し**、その統合と質問リストを
> 介して合流する。**作業者に口頭で聞かない規律(上記)と、聞いた内容を必ず記録する規律は維持する。**
> 経緯: work/2026-08-01-solution-space/catalog.md §0・規10)

## 3. テンプレート(コピペして使う)

```markdown
## スレッド: <タスク名>

### 方針
- なぜ:       <なぜやるか。1〜2行>
- 何を:       <何をするか。1〜2行>
- やらないこと: <スコープ外。1〜2行>
- 触る範囲:   <触ってよいファイル/ディレクトリ>
- 完了条件:   <これが満たされたら完了、と言える条件>

### 判断したこと
- <選んだ案> ← <棄却した案> を採らなかった理由

### 現在地
- 終わったこと:
- 残っていること:
- ブランチ: <branch名>

### AIに出した指示(時系列)
- <指示1>
- <指示2>
```

## 4. 記録シート(合流した人が埋める)

```markdown
## Phase -1 記録: <タスク名>  合流者: <名前>  日付:

1. 引き継げたか
   [ ] メモだけで進められた
   [ ] 進められたが質問が必要だった
   [ ] メモだけでは無理だった

2. 作業者に聞いたこと / 聞きたかったこと(最重要 — 具体的に全部書く)
   -

3. 詰まった箇所と、その原因
   -

4. ★ セッションの中身(AIとのやりとり全文)を見たいと思ったか
   [ ] 思わなかった      → Join は不要
   [ ] 少し思った        → どの場面で? →
   [ ] 見ないと無理だった → どの場面で? →

5. メモに項目を1つ足せるとしたら何か
   -
```

**4番が Phase 2(セッション履歴の移送)を作るかどうかを直接決める。** 必ず埋めること。

> (→ 2026-08-02、この様式は v2 に置き換わった。**現行の様式は `docs/record-sheet.md`**。
> 記録は上書きしないのでここは当時のまま残す。v2 での主な違いは、帰属タグ [A/B/C] と深刻度タグの追加、
> 「brief で足りた箇所」を最低1件書く義務、一致記録(brief だけの仮判定 vs diff を見た本判定)、
> 作業者が埋める7番(合流後の続きは受け入れる内容だったか)、および
> 選択肢から価値ラベル(「→ Join は不要」等)を外したこと —— 合流者が
> 「期待されている答え」を推測できると測定にならないため)

## 5. 判定(1週間後)

2〜3件の記録を並べて見る。

| 見るもの | 判定 |
|---|---|
| 記録シート1番 | 「メモだけで進められた」が過半 → 仮説は生きている |
| **記録シート4番** | 「思わなかった」が過半 → **Phase 2 を延期または中止**。自作は2点に縮む |
| 記録シート2番・5番 | ここに繰り返し現れる項目が、テンプレートに足すべき欠落項目 |

判定結果と、テンプレートに足すことにした項目を proposal.md に反映してから Phase 0 に進む。

> (→ 2026-08-02、この判定表は `docs/run-2a.md` の凍結版に置き換わった。上記3行は当時のまま残す。
> 凍結版では「過半」「頻出」を数値で定義し、brief 無し対照腕(T2)の行を足し、
> 1番の判定を「確証」ではなく「強い仮判定」としている)

## 6. やってはいけないこと

- **完璧なメモを書こうとしない。** 3分で書ける量が上限。それ以上かかるなら運用として成立しない
- **合流者が作業者に気軽に聞いてしまう。** 聞けば当然うまくいくので、実験にならない
- **うまくいったからといって、すぐ作り始めない。** §1 の表のとおり、成功は作らない理由にもなる
- **AIの出力を共有メモに貼る。** 共有するのは人間の指示と判断だけ。量が増えると誰も読まなくなる

> (→ 2026-08-02 撤回。この禁止は「人間が読む」という前提の上に立っていたが、H2 移行で
> 消費者は AI になった。禁止は**人間向けダイジェスト層に限定**し、AI 消費層(brief 本体・
> 最終 ai 全文)は現仕様を維持する。「量が増えると読まれない」という制約は人間向け層には
> 依然実在するため、二層表示を作る場合の上層は AI 出力の貼り付けではなく人間向けに書かれた
> 要約でなければならない。経緯: work/2026-08-01-solution-space/catalog.md 議4)
