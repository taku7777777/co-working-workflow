# 検討: 意思決定の記録と plan をどう管理するか

日付: 2026-07-25(初版コミット日。第8版 §12.1 により 2026-08-01 付与)

**問い**: リポジトリには最新のあるべき状態だけを置きたい。
しかし「何をどう判断したか」「最終結果とは異なるが途中でどんな議論を経たか」は失いたくない。
この2つをどう両立させるか。

**検討方法**: 5つの異なる視点(ADR実務 / gitデータモデル / 運用と人間の行動 / エージェント視点 / 後から調べる人)で
独立に設計案を作らせ、3つの角度(実装可能性 / 運用の現実 / 本来目的との整合)から相互批判させた。

---

## 1. 全案が一致したこと

| | |
|---|---|
| **plan は独立保存しない** | 5案とも一致。既に過程側に自動で入っており、二重化は同期漏れの発生源にしかならない |
| **新しい保存場所はほぼ要らない** | 5案とも「既存の2リポジトリで足りる」。増やすとしても極小 |
| **AI下書き + 人は yes/no** | ゼロから書かせる案は1つもなかった |

## 2. 最も重要な発見 — 索引の強化だけでは原理的に届かない

> **棄却された案は commit を1つも生まない。**
> したがって commitハッシュ↔プロンプトの紐付けグラフに**アンカーが存在しない**。
> 追跡可能性は「起きたこと」に対して完全で、「**起きなかったこと**」に対して構造的に盲目である。

紐付けの仕組みは優れているが、**まさに残したいもの(採らなかった案)には効かない**。
だから「何か」は必要になる。ただし件数は極小(スレッドあたり数件)なので、増やすのは最小でよい。

## 3. 推奨する構成

批判3件のうち2件が同じ案を最良とした。決め手は**劣化の仕方**である。

> 半年運用で問うべきは「生き残るか」ではなく「**人手が止まった時に何が残るか**」。
> 空欄は「書かれなかった」と読める(正直な劣化)。
> 対して「いま有効な決定の一覧」は、剪定されないまま現在形で嘘をつき続ける(高くつき、しかも不可視)。

### 4層。上に行くほど自動、下に行くほど稀。

| 層 | 何を | 誰が | どこに |
|---|---|---|---|
| **0. やりとり** | 指示・AIの説明・plan・議論の全部 | **完全自動** | cowork-state(既存) |
| **1. 紐付け** | どの変更がどのやりとりから生まれたか | **完全自動** | cowork-state + PR本文のID行 |
| **2. 決定** | 決めたこと + **採らなかった案** | AI下書き → 人は yes/no か消すだけ | **PR本文**(→ squash でコミットメッセージに残る) |
| **3. 主題別の記録** | 繰り返し聞かれる決定 | 人(稀) | `docs/decisions/<主題>.md` |

### 層2をPR本文に置く理由

- **レビュアーが必ず見る唯一の場所**。別ファイルに置くとリンクを踏まない限り読まれない。
  issue.md の目的は「判断の妥当性を確認できるようにする」なので、判断材料がPRの外にあっては効かない
- **人が作るファイルが1つも増えない**。認知負荷を下げるのが目的である以上、これ自体が目的への寄与
- **空欄でもマージできる**(ゲートにしない)。書かれなくても壊れない

**下書きの規約**: AIは**実際のターンを引用する。要約しない。**
理由がログに無ければ空欄+「(理由未記録)」と書く。
— これは捏造対策。人が「B」と一言答えただけなのに
AIが「Aはスケーラビリティの懸念があるため却下」と書き、人が読み流して確定すると、
**存在しなかった理由が記録として定着する**。要約させず引用させれば、人は思い出すのではなく
見覚えで検証できるので、確認コストが「自分で書く」を下回る。

### 層3を「需要駆動」にする

決定ファイルを**「決めた時」ではなく「同じ問いが2度目に立った時」に書く。**
3ヶ月後に誰かが「なぜ Redis じゃないんだっけ」と聞いた、その瞬間が起票トリガー。

これで3つの問題が同時に消える:

- **粒度問題**(何を1件の決定と数えるか)— 誰かが実際に聞いたものが1件
- **網羅性の偽装**(3件しかないのは重要度なのか記録漏れなのか)— 全て「実際に欲しがられた」もの
- **書かれなくなる問題** — 必要になった時にだけ書くので、前払いが発生しない

棄却案は「過去の版」ではなく**「なぜ今の形が正しいか」の一部として本文に書く**。
こうすると上書きしても失われないので、ADRの不変性と「最新のみ」の緊張が消える。

## 4. 捨てるもの

| 捨てるもの | 理由 |
|---|---|
| PRごとに decisions ファイルを作る | 前払いの負担。3年で必ず死ぬ |
| `timeline.md` / `INDEX.md` などの生成ファイル | 複数人の coworkd が書くとコンフリクトする。cowork-state の「衝突しない」を破る |
| ID採番 + supersedes チェーン + status 遷移 | git の上にもう一つバージョン管理を実装する行為。受益者がエージェントであって人間ではない |
| 「いま有効な決定の一覧」1枚 | 剪定されず現在形で嘘をつく。しかも嘘だと検知できない |
| commit trailer の構造parse | `%(trailers)` は最終段落しか見ない。Co-authored-by が後段に付くと壊れる → **ID文字列の grep を正規の方法にする** |

## 5. 実測で見つかった、既決事項の穴

| 発見 | 影響 |
|---|---|
| **承認済みの plan は `tool_result` にしかない** | 「ツール出力は共有しない」フィルタだと**ユーザーが編集した最終 plan が失われる**。ExitPlanMode の tool_result は例外的に共有層へ含める必要がある |
| **Claude Code は plan を `~/.claude/plans/*.md` に保存済み** | plan の永続化は既に公式にされている。ただしファイル名がランダムでスレッドと紐づかない |
| **squash merge は feature ブランチの trailer を完全に破壊する** | 実測済み。紐付けの主キーを**コミットハッシュにしてはいけない**。スレッドIDにする |

## 6. 決着した2点

### (a) squash メッセージ設定 → 両対応で解決【決定】

設定はリポジトリごとに違いうるので、**どちらでも動く方式**にする。

**ID行を「各コミットのメッセージ」と「PR本文」の両方に書き、grep で取り出す。**
実測で両設定とも成立した(連結設定ではID行が2回出るが grep では無害)。
rebase merge / merge commit は元コミットが残るのでコミット側のID行が生きる。
→ **4つのマージ方式すべてを1手でカバーできる。**

- 主キーは**スレッドID**(コミットハッシュは rebase/squash で変わるので使わない)
- 取り出しは `%(trailers)` の構造parseではなく**ID文字列の grep**
  (`%(trailers)` は最終段落しか見ず、GitHub が付ける `Co-authored-by` で壊れる)
- コミット側への挿入は **CLAUDE.md の規約**とする
  (`commit-msg` フックは `core.hooksPath` の手動設定が要り、plugin marketplace で配れない)

### (b) タスクの箱は Notion【決定】

**cowork はタスク管理をしない。** タスクの一覧・優先度・担当は Notion が持つ。
cowork は1つのタスクに対応する「作業の過程」だけを扱う。

これにより設計が縮む:

| | 変更前 | 変更後 |
|---|---|---|
| `thread.md` | title, status, 参加者, 対象repo/branch, PRリンク | **Notionタスクへのポインタ + 実行時の状態**(誰のAIが動いているか等) |
| 一覧UI | タスク一覧 | **作業中スレッドの状態一覧**(タスク管理ではない) |

連携は**疎結合**にする。thread が Notion のURLを1つ持つだけで、API連携は当面しない
(この端末では Notion 連携が未整備であり、依存を作ると Phase -1 が止まるため)。

## 7. レビューのトリアージ 【決定】

**問い**: issue.md L12「重要度が高い領域は強度高く、低い領域は強度低く低コストでレビューできるようにしたい」をどう満たすか。
Notion のタスク優先度は**着手前**に決まる値であり、ここで要るのは**成果が出た後**の配分なので別物である。

### 7.0 前提の整理 — L12 は2つの要求に分かれている

| 半分 | 何を制御するか | 状態 |
|---|---|---|
| (a) 低い領域を**低コスト**で | **読む深さ** | **解決済み**。intent.md 10行 → 決定(PR本文) → コード の段階開示と「掘らない自由」(issue.md L24「粒度の大きい全体の方針から段階的に」に対応) |

> (→ 2026-08-02、(a) の「解決済み」を撤回。設計としては解決したが**運用では成立していない**。
> 2026-07-30 の実測(正本 §1)で intent-log は 10スレッド中 2件にとどまり、段階開示の最初の段
> (intent 10行)が大半のスレッドに存在しない。次の段である PR 本文の決定記載(本文書 §3 層2)も
> 決定済みのまま実践ゼロである。**段階開示の3段のうち2段が実在しない**以上、(a) は未達である。
> 処方は intent 起草の発火点を規約化すること(AI が下書きを出し人が確定する)で、
> 経緯は work/2026-08-01-solution-space/catalog.md の規2・規4 にある)
| (b) 高い領域を**強度高く** | **一覧に何が出るか** | **本節の対象**(issue.md L30-32 の一覧要求の上に載る) |

proposal.md §6 の対応表は (a) だけで ○ としていた。ここを **(a)○ / (b)△** に分ける。
**(b) は保証機構ではなく可視性で効かせる**(§5.2 と同じ立場)。効果は未検証の仮説である。

### 7.1 共有の順位づけを作らない。各自のレンズにする

一覧を全員共通の「重要度順」で並べると、上位が「誰かが片付けるべきもの」になる。
止める力を持たなくても、**§5.2 で消したレビュー待ち行列が並び順として復活する**。
しかも先頭に立ち続けるのは事実上いつも同じ人(MGR)であり、非対称性も同時に戻る。

さらに、共有順位は**全員が同じ先頭を見る**ので「誰かがやるだろう」に落ちる。
各自のレンズなら**全員の先頭が互いに異なる**ので、レビューの負荷が分散する。
issue.md の本題(MGRに集中している)への効き方は、こちらのほうが直接的である。

- **共有するのはスレッドの属性(バッジ)だけ。順位は共有しない**
- **一覧の内容は各自のクライアントが決める。既定は「自分がまだ確認していない × バッジが付いている」**
- 全員が同じUIで、それぞれ自分の視点から見る。**MGR用の一覧を作らない**

### 7.2 並べ替えではなく「既定で絞る」

**並べ替えだけでは足りない。** 未確認のスレッドは常に多いので、順位を付けても
一覧は長いままで、「どこまで見れば終わりか」が分からない。よって主機構は**足切り**にする。

- **既定表示 = 自分が未確認 かつ バッジが1つ以上付いているスレッド**
- **バッジが1つも無いスレッドは既定で畳む**(消さない。展開すれば見える)
- 順序はその中での並びに過ぎず、**本質は一覧が短いこと**

「掘らない自由」(読む深さ)と同型の「**見ない自由**」(見る対象)を既定にする。
軽いものを見なくてよいと安心できる根拠が要る、というのが L12 の後半の実体である。

### 7.3 バッジは2軸。合成スコアにしない

信号は性質の異なる2種類に分かれ、**求める反応も違う**。
「決済に触っている」と「異議が付いている」は隣接した順位ではなく別の行動を要求する。
1つの点数に混ぜると「点数が高いから重い」としか言えなくなり、**なぜ重いのかが消える**。
これは §4 で捨てた「いま有効な決定の一覧」と同型の失敗 — **検証できない主張**である。

| 軸 | 信号 | 出どころ | 求める反応 |
|---|---|---|---|
| **A. 変更の性質**<br>(自動・誰が見ても同じ) | リスク階層(認証 / 決済 / 公開API / マイグレーション)**要実測 → 7.5** | 変更パスからの推定。**定義はリポジトリごとの設定ファイル** | **深く見る** |
| | **方針が作業途中で変わった** | `intent.md` の diff | **方針から見直す** |
| | 照合の対象外(REQ-ID が付いていない変更) | §5.4 層3 の残余 | **意図との対応を確かめる** |
| **B. 場の状態**<br>(社会的) | **object が付いている** | receipts | 読む前に**その異議を読む** |

**規約: バッジは必ず根拠へ展開できること。**
「risk: 決済」なら該当パス、「方針変更」なら該当 diff、「object」なら誰の何という異議か。
**展開できない信号は出さない。嘘を検知できる形でしか出さない。**

**軸Bは常に0件でも構わない。** object は誰も止めないので、気づいた人が直接合流して直すほうが速く、
使われない可能性が高い。**軸Aだけで機構は成立する**。Bが空なのは設計の失敗ではない。

### 7.4 「このスレッドは誰の確認も無い」は出さない(前版から撤回)

前版はスレッド単位なら名指しにならないので許容としていた。撤回する。

- チームが小さいほど「誰も見ていない」は「あの人が見ていない」と実質同義になる
- 7.1 の各自のレンズを採るなら**そもそも要らない**。各自が「自分の未確認 × バッジ付き」を見れば、
  重いスレッドは**全員の一覧に出る**ので、放置されるほど誰かに当たる確率は上がる

**「高リスクの変更は必ず誰かが見る」保証が要るなら、GitHub の required approvals で担保する。**
cowork が持つのは配分であって保証ではない(§5.7「作らないもの」と整合)。

**進捗・ステータス(issue.md L30-32)はバッジとは別軸。**
「いま誰のAIが動いているか」「完了したか」は `thread.md` の実行時状態が持つ。
バッジは「重く見るべきか」だけを担い、両者は一覧上で別の列である。

### 7.5 検証していないこと(明示)

| 前提 | 検証状態 | 崩れたときの扱い |
|---|---|---|
| リスク階層のパス推定が意味のある差を生む | **未実測**。該当PRの比率が高すぎれば信号にならない | **Phase 0 で該当比率を実測**し閾値を決める。高すぎればこの信号を落とす |
| 各自が一覧を能動的に開く | **未検証**。通知機構は設計に無い | 開かれないなら一覧UI自体の前提が崩れる(§7 固有の問題ではない) |
| (b) の可視性でレビュー強度が実際に配分される | **仮説**。CHI 2026 の実験は「可視化だけで依存が下がる」までしか示していない | 効かなければバッジを増やすのではなく、足切りの閾値を上げる |

### 7.6 露出について — 保証ではなく規約である

`receipts.jsonl` は共有リポジトリ `cowork-state` にある。
したがって**「他人が誰を確認していないか」は、参加者を列挙すれば誰でも復元できる**。
既定UIが出さないだけであり、**データ層では技術的に防いでいない**。ここを保証と書いてはならない。

対処は規約に置く。既にある「**データを人事評価に使わない**」と同じ層である。

> **他人の未確認を集計・表示する道具を作らない。**

git blame と同じで、データはあるが使い方の合意で運用する。
技術で防ぐには receipts を個人ごとに分離・暗号化する必要があり、
それは「追記のみで衝突しない」という cowork-state の性質を壊すので採らない。

### 7.7 新設するもの — なし

材料は既に全部ある(変更パス / intent.md の diff / receipts)。
**一覧UIのフィルタと表示だけで成立する。**自作3点(指示ログ / 合流 / 一覧UI)は増えない。
