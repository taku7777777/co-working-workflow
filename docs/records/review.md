# レビュー: proposal.md は issue.md の解決策として妥当か

日付: 2026-07-25(初版コミット日。第8版 §12.1 により 2026-08-01 付与)

## 結論

**課題設定と方向性は妥当。ただし「案C(新規開発)」という結論は、現状の比較では正当化されていない。**

- ✓ 課題設定 — 外部データで裏付け済み(実地検証済み、§1)
- ✓ 「判断を第一級データにする」方向性 — issue.md の要求をほぼ網羅
- ✓ 設計の内部品質(承認モデル・変更検知・公開境界) — Gerrit/git-appraise からの借用は適切
- △ **案C(自作)の「正当化」** — 比較表に「GitHub標準機能で作る案」が欠けており、根拠が未成立(§2-B)。案Cが誤りという意味ではなく、選ぶ根拠がまだ揃っていないという意味
- △ **段階導入計画** — 提案全体を支える最重要仮説を検証する設計になっていない(§2-E)

> **開示**: この proposal.md は前セッションで私(Claude)が作成したもの。自己レビューのバイアスを避けるため、
> 引用データと案B却下の根拠を実地で再検証した上で、特に「§1 で自己言及済みだから処理済み」に見える
> 箇所を疑って読んでいる。

## 2. 計画を変えるべき指摘(4件)

### [重大] B. 比較表に「案A+ = GitHub標準機能で作る案」が欠けている

§3 は案Aを「判断は共有されるが承認・変更検知・一覧がなく形骸化しやすい」と評価している。これは案Aの過小評価。
proposal が設計した機能のほぼ全ては、GitHub の標準機能 + 小さな Actions で実現できる:

| cowork の機能 | GitHub-native での実現 | 追加開発量 |
|---|---|---|
| L1/L2/L3 判断ファイル | 対象repo `docs/decisions/*.md` | 0 |
| 承認 | PR review approve(真正性・署名は GitHub が担保) | 0 |
| 承認者マトリクス | CODEOWNERS(パス別の必須レビューア) | 0(※) |
| outdated 検知(承認後の変更) | Actions で content_hash 計算 → status check | 数十行 |
| 実装先行の検知 | 同 Actions で承認時 commit と比較 | 数十行 |
| タスク一覧・ステータス・バッジ | GitHub Projects(カスタムフィールド) | 0 |
| 判断リンクなしPRを弾く | Actions の必須チェック | 数十行 |
| 判断のコンテキスト自動注入 | CLAUDE.md / slash command で `decisions/` を読ませる | 数行 |
| 判断の下書き生成 | Claude Code の SessionEnd hook → ローカルでファイル生成 | 小 |

※ CODEOWNERS はパス単位のルーティングなので、proposal の risk tier × 判断レベルのマトリクスに完全対応はしない。
tier をディレクトリに写像する必要があり、tier 変更時にファイル移動が生じる摩擦がある。ただし
「tier ごとのディレクトリを切る」で実務上は回せる範囲で、下の結論(残差は3点)は変わらない。

**GitHub では本当にできないことは、突き詰めると3つだけ**:

1. **秒単位の同期とライブ状態**(GitHub は push 起点なので分単位・確定後。「いま誰のAIが動いているか」は出せない)
2. **複数リポジトリ横断の単一サイドバー**
3. **ローカルファイル操作の体験 + ローカル通知**

したがって案Cの本当の意思決定は「判断を構造化すべきか」ではなく、
**「この3つが 8〜12週の開発 + MGR自身が保守者になるコストに見合うか」**。
proposal はこの問いを立てないまま案Cを推奨している。

補足リスク: 「レビューが律速で困っている本人」が新ツールの開発・保守を抱えるのは自己矛盾になりうる。
案Cの保守コストは「中」と書かれているが、**MGRの時間で払う**点が評価に入っていない。

→ **§3 の比較表に案A+ を追加して再評価すべき。案Cの是非はその後。**

### [重大] A. 最大の律速(pickup time)に対し、施策は新しい待ち行列を追加している

§1 は「単純にやると待ち行列がPRからL1方針に移るだけ」と自認し、楽観的着手とSLAを緩和策に置いている。
しかし **認めたことと解いたことは別**:

- **緩和策の正味効果を計測する仕組みがない**(こちらが本質的)。効果指標に **「L1承認の pickup time」が入っていない**(現在は PR の pickup time のみ)。cowork が自ら生み出す待ち行列を計測しない設計になっており、「PRの待ち時間は減ったが L1 の待ち時間が増えただけ」を検知できない
- **§5 の効果表現が過大**。§5 は L1 を「受理率32.7%(捨てPRの山)」への対策として対応づけ、「方向性の誤りを実装前に**止める**」と書いている。しかし楽観的着手(high 以外は L1 公開と同時に実装開始可)を採る以上、実装は止まらない。実効は「無駄になる作業を**早く打ち切る**」までであり、捨てPRの総量が減るとは限らない(作業は既に走っている)。効果仮説をその水準に書き換えるべき

→ 効果指標に「L1承認の pickup time」を追加し、§5 の効果表現を「止める」から「早期に打ち切る」に修正する。

### [重大] E. 提案全体を支える最重要仮説が、Phase 0 で検証されない

提案は「**10行のL1でMGRが方針の妥当性を判断できる**」に全面的に乗っている。
これが偽なら結局 L2/L3 を掘ることになり、削減効果はゼロ。どんなツールを作っても救えない。

ところが Phase 0 のゲートは「運用が回りL1レビューの効果の兆候が見えたら」と曖昧で、
計測3項目(pickup time / レビュー時間 / 捨てPR率)は**どれもこの仮説を直接テストしない**。
加えて 2〜3週のベースライン計測は AI の PR 生成量の変動でノイズが大きく、差が出ても解釈できない。

→ **Phase 0 の前に「Phase -1」(1週間・コスト実質ゼロ)を置く**:

1. 次の 5〜10 本のPRについて、作業者が実装前に why / what / やらないこと を各3行、Slack か issue に書く
2. MGR はそれだけを読んで、結果を記録する:
   - (a) 方向性を approve できた
   - (b) 掘る必要があった(どこを掘ったか)
   - (c) 読んでも判断できなかった
3. **(a) が過半 → 仮説は生きている。(c) が多い → 3階層の粒度設計から見直し。(b) が多い → 掘った先を L1 テンプレートに繰り上げる**

これが本物の go/no-go ゲート。ツールもリポジトリも要らない。

### [中〜重大] D. 採用インセンティブが「罰」に寄っており、順序が逆

「承認済みL1リンクのないPRはレビューしない」は MGR の権力行使で成立するルール。
失敗した場合の症状は **pickup time のさらなる悪化** — まさに直したい指標が悪化する。

一方、書く側の直接便益(コンテキスト自動注入・引き継ぎ容易化)は Phase 1 提供とされている。順序が逆。

→ **Phase 1 のスコープを「MGRのための見える化」から「作業者のための判断ファイル活用」に変更する**。
指示が短くなる・翌日の再開が速い・引き継げる、が先に効けば、書く行為は罰なしで自走する。
見える化はその副産物として後からついてくる(判断ファイルが書かれていなければ、見える化する中身自体が無い)。

## 4. 軽微な指摘

- **アーカイブ/GC 方針がない** — 1承認=1ファイル、1イベント=1ファイル。完了タスクのアーカイブ規約がないと state リポジトリが線形肥大し、fetch 数秒間隔と合わさって重くなる。git-appraise / git-bug は ref namespace 分離で対処している
- **fetch 数秒 × Nメンバーの現実性が未検証** — SSH 経由の git fetch は API rate limit 対象外だが GitHub の abuse detection はある。常用前に実測が要る
- **署名必須(SSH/GPG)は Phase 2 では過剰の可能性** — 社内・信頼前提のチームで鍵設定の導入摩擦に見合うか。「エージェントが承認を書けない」担保は MCP API の分離だけでも成立する(監査要件があるなら妥当)
- **効果指標の測定可能性** — pickup time / 捨てPR率 は GitHub API で取れるが「レビュー1件あたり所要時間」は取りにくい。最重要の「MGRの認知負荷」は主観指標(週次5段階など)の併用が要る
- **§6 の未決6点のうち 1(state 置き場)と 6(PRマージ条件統合)は骨格に効く** — 特に 1 は §2-B と直結する。対象repo内 `.cowork/` を選ぶなら、案A+ とほぼ同じ土俵に立つことになる

## 5. 推奨アクション

§6 の6点を議論する前に、まず以下を片付けるのが順番として正しい:

1. **Phase -1(1週間・コスト0)を追加** — L1仮説の直接検証(§2-E)
2. **§3 の比較表に案A+(GitHub-native)を追加して再評価** — 案Cの是非はその後(§2-B)
3. **Phase 1 のスコープを作業者便益に変更**(§2-D)
4. **効果指標に「L1承認の pickup time」を追加し、§5 の効果表現を実態に合わせる**(§2-A)
5. **issue.md 要求との差分表(本レビュー §3)を提案書に取り込み、劣化2点を明示**
6. **EASE 2026 の引用を修正、PRサイズ +154% の出典を確認**(§1)

いずれも提案の骨格を否定するものではなく、**「作る前に確かめる」順序の修正**。
1 と 2 の結果次第で、そもそも案Cを作らずに済む可能性がある — それが最大の節約になる。
