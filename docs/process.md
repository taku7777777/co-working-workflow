# プロセス規約

このリポジトリでの**仕事の流し方**。成果物をどこに置くかは AGENTS.md が定める(この文書では繰り返さない)。
各規約の根拠と検討経緯は `work/2026-08-01-solution-space/catalog.md` にある。

**原則: 人間の能動アクションは3つの瞬間だけ。** 開始の確定、分岐の選択、締めの1語。
それ以外は AI が起草し、人は確定する。規約が重いと感じたら**足すのではなく削る**。

## 5介在点 — 誰が・いつ・何をするか

| # | 介在点 | いつ | AI(起草・自動) | 人(確定のみ) |
|---|---|---|---|---|
| 1 | 意図の付与 | 最初の実質指示の直後。**brief の方針が空だと判明したときだけ**(pull 型) | 先頭プロンプトとそれが参照するファイルから intent 5項目を起草。ファイル書き込みは**確定後のみ** | 1分以内で確定/修正/不要 |
| 2 | 途中の判断 | 分岐の都度 | AskUserQuestion で構造化(自由文で聞かない) | 選ぶだけ。これが記録そのもの |
| 3 | 中断と再開 | 区切り / 再開時 | 「締めて」で4節サマリ。再開時は brief を読む | 「締めて」の1語。再開時は brief 読了 |
| 4 | レビューと承認 | PR 時 / 合流時 | brief と diff から質問リスト・人間に見てほしい箇所・receipt 下書きを起草。**receipt は AI が打たない** | **「brief だけの判断」と「成果物を見た判断」が一致したかを1行** |
| 5 | 習熟と展開 | 週1回・5分 | 週次の集計を state から起草 | 主観5段階1行+気づいた不足を最大1行(**検証記録に現れた不足だけ**) |

## 帰属コンパス

合流・レビューで「分からなかったこと」には必ず3分類のタグを付ける。投資判断はこの分布だけを見る。

- **[A]** 記録に在るが見つけられなかった → 提示層(brief)への投資候補
- **[B]** 記録自体に無かった → 捕捉層(Tier 1)への投資候補
- **[C]** リポジトリ/成果物を見れば分かった → **何も作らない**(読む場所の指示を1行足すだけ)

## 規約

### 介在点1 — 意図の付与

1. **intent 起草の発火点**: 最初の実質指示の直後に AI が intent 5項目の下書きを提示し、人は確定・修正・不要を返す。**完了条件だけは AskUserQuestion 1問で確定する**(プロンプトに現れにくい要素を既存の捕捉チャネルへ流し込むため)。
2. **unfiled が既定の受け皿**: `task new` は3条件のみ — 複数リポジトリ / 4時間以上かつ検証可能な完了条件 / 実際に合流予定がある。
3. **参照ファイルと handoff の複製**: 先頭プロンプトが参照したローカルの `.md` は、そのスレッドの `work/` へ複製する。handoff を生成したときも同じ。**唯一実証済みの引き継ぎ機構が共有境界の外に残らないようにする。**

### 介在点2 — 途中の判断

4. **判断は AskUserQuestion を通す**: 自由文で聞かない。唯一質の高いチャネルであり、brief 最大の空欄の原料になる。
5. **方針を覆すときも AskUserQuestion を通す**: 選択肢の文言に「(従来: X を Y に変更)」を含め、AI は intent.md の修正案を同時に起草する。人は確定するだけ。**方針節と判断節が矛盾したまま残らないようにする。**
6. **委譲プロンプトの復唱**: Codex へ委譲した直後に、AI は委譲プロンプトの要旨を人間向けの発言として復唱する。最も意図が濃いテキストが記録ゼロになるのを、実装なしで防ぐ。

### 介在点3 — 中断と再開

7. **「締めて」→ 4節サマリ**(目的 / 現在地 / 判断したこと / 未解決)。**「未解決」節には小見出しを3つ立てる** — 未処理物(宙に浮いた commit / PR / TODO)、次の一手の候補と推奨、**意図的にやらないと決めたこと**(後回しと忘却を区別し、合流者のスコープ勝手拡大を防ぐ)。
8. **相談系セッションの明示分類**: 質問だけ・master 上のセッションは記録はするが引き継ぎ対象にしない。
9. **cowork-state の日次ローカルコミット**: SessionStart に1行。**push はしない**(決定 A)。

### 介在点4 — レビューと承認

10. **PR 本文の4項コントラクト**: 意図(brief 目的節の転記)/ 動作証明 / リスク開示+**採らなかった案** / 人間に見てほしい箇所(file:line 限定)。AI が起草し人が確定する。
    - **動作証明は人間の一人称宣言「私は動かした: <コマンドと結果1行>」で、AI は書かない。** AI は欄を**空欄のまま出す**。文書のみの変更など動作証明が原理的に存在しない場合は「該当なし」と理由を1行書く。**実行していない検証コマンドを書かない**(尤もらしい1行を埋めるのが最も起きやすい違反)。
    - 棄却した案は commit を生まないため、書かなければ永久に残らない。空欄可。
11. **小 diff 規律**: スレッド1本 = PR 1本 = 目安400行以下。超えそうなら AI が分割を提案し人が確定する。
12. **ID 行は1形式に固定**: `Cowork: <qualified-id>` をコミット本文末尾と PR 本文の両方に。2形式の併存は grep 導線を壊す。

### 介在点5 — 習熟と展開

13. **週次評価の受け皿**: `work/` 配下の週次1ファイルに追記する — 日付 / 主観5段階1行 / 不足を最大1行 / 帰属 A・B・C の分布。あわせて、その週の `kind:answer` から AGENTS.md・この文書へ昇格すべき恒常ルールの候補を AI が起草し、人が確定する。

## 検証中の特例

Phase -1 の判定が出るまでは、**Tier 0 以外の実装を増やさない**。
新しいゲートも増やさない(既存の1個 =「記録シート未記入ならレビュー依頼しない」のみ)。
合流の手順と記録様式は `docs/record-sheet.md` にある。

**あなたが Run 2a の合流者(JN)としてこのリポジトリに入っている場合は、
`docs/run-2a.md` と `work/` 配下を開かないこと。** 判定条件を知ると記録が
「期待されている答え」に寄り、測定が成立しなくなる。開いてしまったら記録シートにその旨を書く。
