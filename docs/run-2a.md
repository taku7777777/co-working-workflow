# Run 2a 手順書(作業者 = OP 用)

Phase -1 の第二段階。K1(自己盲検・仮合格)の次に、**第二の人間(JN)による読む合流**を測る。

**この文書を JN に渡さないこと。** JN に渡すのは `docs/record-sheet.md` と `cowork brief` の
出力だけ(検7)。計画・提案・判定条件を読ませると、記録シートの回答が
「期待されている答え」に寄って測定にならない。

## 何を測るのか

仮説は **H2:「brief は AI が消費し、人間は AI の統合・説明を介して合流する」**。
K1 で H1(brief 1枚で人間が直接引き継げる)は棄却済み。

H2 には既知の交絡がある —— 合流が成功しても、brief の寄与とリポジトリ自体の寄与を分離できない。
そのための対照腕が下の T2 である。

## 腕の構成

| 腕 | 内容 | 最低本数 |
|---|---|---|
| **T1** | 標準 brief 腕。全計器を回す。**OP 終了から3日以上空けて**合流する | 2本(判定が割れたら3本目) |
| **T2** | **brief 無し対照**。同じ JN・別タスクで、JN の AI にはリポジトリと PR 履歴だけを渡す | 1本 |

GitHub-only 腕(T3)は Run 2a では実施しない。棄却ではなく Run 2a 後へ持ち越す。

**判定は T1 のシートで行う。** T2 は「brief 無しでも同等に進めたか」を見る対照で、
T1 と同等に進めた場合は brief の寄与を疑う材料になる。

## Run 2a を始める前にやること

1. **brief vs 生ログの ablation(半日)** — 同一スレッドで「brief を渡した cold read」と
   「生の `sessions/*.jsonl` を渡した cold read」を別コンテキストで比較する。
   人間向けの整形が AI 消費者に必要かを、Run 2a のタスクを消費せずに測れる唯一の経路。
2. **計器の健全性確認** — hook が静かに全滅していないか(SessionStart での state 乖離検査)。
   壊れた計器で測ると偽陰性が出る。
3. **cold read リハーサル** — 下記の手順で JN に渡す前に毎回実施する。

## タスク選定

- **OP が選ばない。** 候補一覧から JN 側または機械的に選ぶ(OP が選ぶと
  「brief が書きやすいタスク」への選択バイアスが入る)。
- 粒度はジュニアが4〜8時間で終わる程度。検証可能な完了条件が書ける。
- **cowork 自身の開発タスクは1件まで**(メタ循環の回避)。
  このリポジトリのタスクを選ぶ場合、JN のセッションは `CLAUDE.md` 経由で `docs/process.md` を
  自動で読み込む。process.md 末尾に「合流者は run-2a.md と work/ を開かない」と明記してあるが、
  **隔離が約束に依存する状態になる**。確実に隔離したいなら、この1件は T2(brief 無し対照)へ
  割り当てるか、判定の分母から外す。
- **1本は「境界プローブ」にする** —— 完了条件が書けない探索・デバッグ系を意図的に選び、
  そうとラベルを付けて記録する。**この1本は判定の分母に入れない。**
  検証の母集団と、実際に困っている問題の母集団がずれるのを検出するため。
- JN への事前レクチャーはしない。

## 各タスクの進め方(OP 側)

1. **cold read リハーサルと事前予測** — brief 本文だけを別コンテキストのサブエージェントに渡し、
   4節(目的 / 現在地 / 判断したこと / 未解決)**それぞれについて行動を決められるか**を判定させる。
   全体二択にしない。**その予測を先に共有ドキュメントへ書いてから** JN に渡す。
   予測が当たれば安価な brief 品質門番が手に入り、外れればこの手法を棄却できる。どちらでも利得がある。
2. **計器の目視(1分)** — brief を貼る直前に `sessions/` の件数と最終 ts を目視し、
   記録シートのヘッダに書く。
3. **brief は verbatim で貼る** — `cowork brief` の出力そのままと、cowork のコミットハッシュを併記する。
   **手直ししない。** 手直しすると測っているのは brief ではなく OP の編集能力になる。
   どうしても直した場合は、直した内容を「計器の欠陥ログ」として別枠に記録する
   (それが次の投資判断の入力になる)。
4. **読み戻しに1行で返す** — JN の AI が出す「現状統合+質問と仮定」に対し、
   「訂正あり / なし」+1行だけを返す。訂正した内容は brief の欠陥データなので帰属タグを付けて残す。
5. **記録シート7番を OP が埋める** — JN の続きが受け入れる内容だったか、逸脱は何か。
6. **1本だけ AI 合流者レビューを試す** — JN の AI に brief と diff から質問リストと
   「人間に見てほしい箇所」(file:line 限定)を起草させ、人は確定だけする。
   Run 2a が「合流」だけでなく「レビューコストの低減」も測るようにするため。

検12 はカタログに「**検証前の今しか判定表を直せない**」と事前登録された唯一の入力で、

それ以外の入力 —— とくに Run 2a のシートを1枚でも見た後の修正 —— は認めない。

(初版では凍結の基準を「本ファイルの初版コミット」としていたが、この例外条項を足す変更自体が
初版との差分を作り、宣言が自分で自分を偽ることになるため、基準をマージコミットに移した。
判定表の中身は初版から変えていない。)

用語は数値で固定する:

- **過半** = T1 の判定対象タスク数の過半(境界プローブは分母に入れない)
- **頻出** = タスクを横断して2回以上
- **1勝1敗なら T1 の3本目を必ず実施する**

| 見るもの | 判定 |
|---|---|
| シート1番「メモだけで進められた」が過半 | 合流仮説の**強い仮判定**(確証とは呼ばない。1 JN ではタスク間が独立でなく、2本目以降は学習効果で下駄を履く) |
| シート4番「全文を見たいと思わなかった」が過半 | **Join を作らない**判断の材料とする |
| シート4番「見ないと無理だった」が1件 | その場面を最小仕様の入力として保存する。**それでも即作らない** |
| 帰属 A が頻出 | 提示層(brief)への追加投資を検討する。**ただし投資の前に、まず「生ログをそのまま渡す」を試す**(2026-08-02 追記・検12 の結果。brief は最終応答以外を200字に切っており、切り詰めをやめるほうが提示層への投資より安い) |
| 帰属 B が頻出 | 捕捉層(Tier 1)の該当項目を解除する |
| 帰属 C が頻出 | **何も作らない**(読む場所の指示を1行足すだけ) |
| シート2番・5番に同型の項目が**2回以上**(K1 の2箇所は1回と数える) | intent テンプレか4節サマリに追記する。**それ以外は足さない** |
| 一致記録(brief だけの仮判定 vs diff を見た本判定) | 一致するなら「brief で軽く済ませ、必要な所だけ掘る」が成立している証拠 |
| T2(brief 無し)が T1 と同等に進めた | **brief の寄与を疑う。** 提示層への投資を止めて再設計する |
| intent 確定が毎回3分超 | pull 型でも重い → テンプレを**削る**(足さない) |
| 「1日に cowork へ使った分数」が増加傾向 | 北極星(低コスト・低認知負荷)に反する → **規約を削る** |
