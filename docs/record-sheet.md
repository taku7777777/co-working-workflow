# 合流の手順と記録シート(v2)

**合流する人(JN)が読むのはこの文書だけです。** これと `cowork brief` の出力の2つが、渡される全部です。
他のリポジトリ内文書(提案書・計画・仕様)は読まないでください —— 読むと、この記録が
「期待されている答え」に寄ってしまい、測定になりません。

---

## 手順

### 1. brief は自分で読まず、まず自分の AI に渡す

貼られた brief を自分で読み下そうとしないでください。**自分のセッションの AI に brief 全文を渡し、
次の2つを出させてから**作業に入ります。

1. **現状統合** — 何のタスクで、どこまで進んでいて、次に何をすべきかを 1〜2千字で
2. **質問リストと、置いた仮定** — brief から読み取れなかったこと、推測で埋めた箇所

### 2. AI に裏取りをさせる

brief に書かれたリポジトリの状態(マージ済み・テスト通過・ファイルの場所など)は、
**必ず実際のリポジトリと突き合わせてから**続きに入ってください。
brief が確信を持って事実と違うことを書いている実例が既に出ています。

### 3. 読み戻しを1往復だけ行う

上の「現状統合+質問リストと仮定」を共有ドキュメントに貼ります。
作業者(OP)は **「訂正あり / なし」+1行** だけを返します。それ以上のやりとりはしません。

- **作業者に口頭で聞かないでください。** brief だけで足りるかを測っているので、
  聞けてしまうと実験が成立しません。
- どうしても詰まったら聞いてよいですが、**何を聞いたかを必ず記録してください**(これが最も重要なデータです)。

### 4. 続きを1手進める

自分の Claude Code で作業し、PR を出します。

### 5. PR を出したら、一致記録を取る(順番が重要)

1. **先に**、brief(と AI の統合)だけを見た段階での PR への仮判定を**1語**で書く —— `LGTM` / `要修正` / `判断保留`
2. **そのあとで** diff を開き、本判定を書く
3. 一致したか・しなかったかを1行

順番を逆にすると測定になりません。

### 6. 記録シートを書く

**PR のレビュー依頼を出す直前に記入し、コミットします。** 未記入ならレビュー依頼をしません。
デブリーフ(OP との振り返り)の**前**に書き切ってください。会話のあとは追記だけ可能で、書き換えはしません。

各項目に帰属タグを付ける:

- 🟢 [ ]

- [ ] 見ないと無理だった → どの場面で:
